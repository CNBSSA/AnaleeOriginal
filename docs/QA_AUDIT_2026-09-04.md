# Analee — QA audit record, 2026-09-04

Standing defect register for `AnaleeOriginal`. **Written because GitHub Issues
are disabled on this repo**, so there was nowhere durable for findings to live —
they existed only in a chat transcript, which is exactly the fragility Festus
has named. Update this file when a finding is fixed or a new one is verified.

An audit pass reported findings against `main` at `786a4e0`. Every item below
was **re-verified against the live tree** before being recorded; two of the
original claims did not survive that check and are corrected here.

---

## Fixed in this pass

### 1. OCR silently backdated unreadable dates to today — ACCOUNTING INTEGRITY
`ocr/routes.py` (`confirm_receipt`). A row whose date failed to parse was given
`datetime.utcnow()` and imported anyway:

```python
except (TypeError, ValueError):
    date_value = datetime.utcnow()     # silently "today"
```

The books looked complete, the transaction sat in whatever VAT/tax period the
import ran in, and nothing recorded that the date was invented. It sat next to
an inconsistency that makes the intent clear: an unreadable **amount** already
dropped the row — only the **date** was fabricated.

**Fixed.** The row is refused and named ("rows 2, 3 — type each date as
YYYY-MM-DD"), so the user can correct it on the review screen they came from. A
partial import is never reported as a clean one.
Tests: `tests/test_ocr_invalid_dates.py` (4). Proven toothed — restoring the old
line reproduces the defect exactly (`Bad date` stamped `2026-09-04`).

### 2. Password reset was takeover-shaped — AUTHENTICATION
`auth/routes.py`. `reset_password(token)` **never read the token**. It looked up
a user by an email posted in the form and reset that account's password.

It was **not exploitable**: `ResetPasswordForm` has no email field, so
`form.email` raised and every submission returned HTTP 500. The danger was the
trap — anyone "fixing the 500" by adding the missing field would have shipped
**unauthenticated account takeover of any user, including an admin**.

The request path was also broken and leaky: it sent no email (there is no mailer
in this app) while flashing "check your email", and answered
*"Email address not found"* for unknown addresses — a free membership checker.

**Fixed.** New `password_reset_tokens.py` follows the existing house pattern
(`client_explain_tokens`, `reports/tb_share_tokens`, `provisioning`):
`itsdangerous` off the app secret with a purpose salt, one-hour expiry,
**user-bound**, and **bound to the password hash at issue time** so the token
dies the moment it is used — single-use with no schema change. The route
resolves its target from the token only; the request path returns one identical
answer either way.
Tests: `tests/test_password_reset.py` (10), including
`test_the_takeover_trap_stays_shut`, a source-level guard that fails if anyone
reintroduces an email/user lookup into that view. **Do not delete that test to
make a change pass.**

### 3. The login page swallowed every message sent to it — found during the above
`auth/routes.py` (`login`). The view begins with `session.clear()` for
session-fixation hygiene, which also emptied the flash queue. Every message that
redirected to the login page — including "your password has been reset" — was
destroyed before the page rendered. The user saw silence.

**Fixed.** The flash queue is preserved across the clear; the clear itself is
unchanged. This was **not** in the original audit.

## Corrections to the original audit

### The hard-coded admin credential is NOT remotely reachable
The audit stated the credential "can create or reset a privileged account." On
this code it cannot:

* `create_admin_if_not_exists()` (`auth/routes.py`) has **zero callers** and no
  route decorator — dead code.
* `create_admin.py` is a standalone script; the Procfile is `web: gunicorn`
  only, so it never runs on deploy.

**It is still not cleared, for a different reason.** Dead code does not unwrite a
database row. If that script was ever run against production, an admin account
with that password exists in the live database now. Nothing in the repo can
answer that — only a login attempt against production can.
**Open. Owner: Festus.**

Related and confirmed: commit `71eef5a` ("remove hardcoded admin123 credential,
use env vars") exists in history and is an ancestor of **neither `main` nor
`develop`**. A security fix was written, committed, and never landed. That
process failure is the most important finding in the audit.

### Password reset was misfiled as an availability problem
The audit recorded it as broken recovery (customers locked out). That outcome was
right, but the classification hid the real risk — the takeover-shaped logic
underneath — and would not have prioritised it correctly. See item 2.

## Automation-programme pass (2026-09-06/07) — verified and fixed

Found during Festus's scoped re-open for automation ("more automation until
nothing to automate"). Recorded here because Issues are disabled and these
otherwise live only in PR descriptions. All shipped and promoted; each is
covered by a regression test, and the source-level guards are named where one
exists.

### A. A statement was reported "All processed" before anything was categorised
`services/analyze_processing.py`. A row counted as finished if it had **either**
an account **or** an explanation. Both import paths stamp the chosen bank
account onto every row (`bank_statements/services.py`, and the "assign all rows
to account" selector on the OCR review screen), so `unprocessed_count` was 0 the
instant an import landed: the analyze list showed a green "All processed" badge,
the exceptions view had nothing to show, and auto-processing never saw the rows.
**465 live transactions on Festus's own account** sat uncategorised and
unexplained behind that badge. A row is now done only with **both** halves —
which is what the UI label and the function's own docstring already claimed.
Tests: `test_analyze_processing.py::test_imported_statement_is_not_reported_all_processed`.
*Note: the old rule was deliberate and test-pinned, so this is a behaviour
change Festus approved, not a typo fix.*

### B. Auto-process sent every tenant's chart of accounts to the model
`PredictiveFeatures.suggest_account(..., user_id=None)` falls back to
`Account.query.filter_by(is_active=True)` across **all users**. The single-row
route passed `user_id`; the batch path did not. Other customers' account names
went into the prompt, and suggestion quality suffered from this user's real
accounts being drowned in foreign ones. The batched engine now takes an
explicitly scoped chart, so there is no `user_id` that can default to `None`.
Test: `test_batch_sends_only_the_owning_users_accounts`.

### C. Two endpoints returned 500 on every call, losing the user's edit silently
`routes.py`: `data.get('account_id', type=int)` on the plain dict from
`request.get_json()` — `dict.get()` takes no keyword arguments — raised
`TypeError` in `save_transaction` (the account dropdown auto-save) and
`replicate_explanation_api` (Recall). The browser only wrote to
`console.error`, so an accountant changed the account, saw no confirmation, and
lost the change. Tests: `tests/test_tier0_automation_unblock.py`; proven toothed
(restoring the old line reproduces the 500).

### D. Reconciliation reported repairs it never performed
`bank_statements/reconciliation.py` contains no `delete`, no date rewrite and no
`commit` anywhere — it only counts. The UI nevertheless said "removed N
duplicates, fixed N invalid dates". Stats renamed to `duplicates_found` /
`invalid_dates_found`; the flash and the AJAX modal now report findings and state
that nothing was changed. **Removal stays un-automated deliberately:** the
duplicate rule groups on date+amount+description, so two genuine identical
charges in one day are indistinguishable from a double capture, and a one-click
button must not silently delete accounting records. Source guard:
`test_reconcile_flash_never_claims_removal`.

### E. "Ask Analee" steered the accountant into posting to a bank account
`/api/icountant/<id>/insights` returned the **first three accounts in the chart**
with an invented `confidence: 0.5` and the reason "Alternative suggestion based
on available accounts" whenever the AI category did not map. That fired for
nearly every transaction: the category vocabulary is `nlp_utils`'
personal-finance list (`groceries`, `dining`, `personal_care`…) while
`Account.category` only ever holds Assets/Liabilities/Equity/Income/Expenses, so
only `income` can match at all. The first three accounts of a seeded chart are
Bank Cheque Account 1/2/3 — and `icountant.html` **auto-selected suggestion[0]
into the dropdown**. Books-corrupting, not merely misleading. Same rule as
`57ee9a9`: it now declines rather than guessing.
Tests: `tests/test_no_fabricated_confidence.py`.

### F. The expense forecast asserted a precision it never computed
`overall_confidence: 0.85` and `reliability_score: 0.80` were hardcoded literals
nothing recalculated, rendered as "85.0%" / "80.0%" on the page **and in
`pdf_templates/forecast_pdf.html`** — a document an accountant can hand to a
client. Replaced with `months_observed`, counted from the data, and a statement
that the range is the observed spread and not a prediction interval. No invented
methodology was substituted for the invented number.

### G. Auto-process permanently skipped rows it could not assign
Auto-applied rows leave the `account_id IS NULL` result set, so advancing the
offset by the full batch size stepped over that many still-unassigned rows and
never returned to them. The window now advances only past the rows that remain.
Test: `test_batch_does_not_skip_rows_it_could_not_complete`.

### H. `explanation_source` was recorded and displayed nowhere
Every explanation write was tagged (machine vs accountant vs client), but no
template or script referenced the column — so with automation writing at scale
an accountant had no way to tell a machine-written line from their own, and no
way to target review. Author badges, a per-statement summary, and `?view=ai`
now surface it. Tests: `tests/test_provenance_visible.py`.

### Correction accepted (Festus, 2026-09-07)
Auto-process-on-import shipped **defaulting ON**, which meant importing a
statement silently started AI work and spent Anthropic credit without anyone
asking. Festus flipped it dark (`ANALEE_AUTOPROCESS_ON_IMPORT=1` to enable), to
match every other Analee capability. Recorded because the original default was
the wrong call, not a bug: a capability that spends money should be opt-in.

## Interim note on recovery

There is no mailer in this app, so a reset link cannot be delivered. Rather than
say "check your email" and send nothing, the request page now tells the user to
contact support if nothing arrives. For unsticking a specific customer,
`ANALEE_PASSWORD_RESET_LOG_LINK=1` writes the link to the Railway log (which
Festus can read without a shell). It is **off by default and must stay off** in
normal running: a reset link in a log file is an account-takeover token in a log
file. Turn it on, help the customer, turn it off.
